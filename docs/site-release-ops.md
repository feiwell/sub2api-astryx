# 整站候选版本与生产发布

一个版本固定两个值：官方 `Wei-Shaw/sub2api` 的 release tag，以及本仓已在 `main` 通过 CI 的 40 位提交 SHA。只改前端时沿用现网后端 tag；只升级后端时沿用已批准的前端 SHA。不要把当前最新 tag 和最新前端 SHA 交给两套各自运行的定时器。

## 准备候选包

在 GitHub Actions 选择 **Prepare site release → Run workflow → main**，填写后端 tag 和前端 SHA。在测试和上传都成功后记录正式运行的 run ID、main 的 SHA、artifact ID 和下载摘要。PR 预览、分支产物、失败或跳过联合测试的运行都不能上线。工作流没有生产凭据；绿色运行仅表示候选包已准备好，不表示线上版本已改变。

## 首次接入生产（需要生产管理员）

- 用主机端只读凭证下载已批准的指定 run，而不是把生产 SSH 或 Docker 权限给 GitHub。固定仓库、工作流、分支、事件和 SHA；检查 GitHub 提供的 artifact 摘要和包内校验文件。禁止从下载的归档中执行安装脚本或从输入接受任意命令。
- 应用前记录线上运行的后端实际版本、前端挂载地址/摘要和公开入口；保留可恢复的数据库备份以及上一对后端和前端。不能验证备份或数据库迁移能否安全回落，停止发布，不能用开机健康检查代替恢复测试。
- 发布器应串行运行，先准备两端再切流。不要在生产连接上并行启动新旧后台来测试迁移；使用测试数据库或已隔离的副本。未变化的一端跳过重建；不更新 PostgreSQL、Redis，不因升级前端而重启后端。须保留站点已有的代理规则、CSP、安全配置和数据挂载。
- 切换后同时核对：运行中的后端版本、公开设置 API、控制台路由、HTML 引用的脚本与本次前端包的哈希。任何一项失败都不记为整站发布成功；若数据库已发生不向后兼容变更，进入维护/人工恢复流程，不自动启动旧后端。

**现状边界：**本仓工作流不操作生产。管理员首次接入可信的整站部署命令前，不要先点后端原生更新，再试图补上前端。
